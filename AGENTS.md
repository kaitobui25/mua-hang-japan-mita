# Mita Japan — Agent Rules

## Start here
- **Use current evidence:** follow the latest user decisions and actual code/runtime. `.agents/chatgtplog/` records past incidents, not permanent specifications; older README/runbook instructions may have been superseded. Resolve conflicts before acting.
- **Project map:** Next.js storefront `src/`; Fastify API/auth/workers `backend/src/`; PostgreSQL SQL/migrations `backend/src/db/`; backend tests `backend/tests/`; WinForms, lifecycle and sync `scripts/`; operations `docs/` and `deploy/mita/`.
- **Inspect first:** `git status --short`, affected code, `git diff --check`, running processes and actual target. Local API `127.0.0.1:4000`, PostgreSQL `127.0.0.1:5433`; `15432` is a temporary tunnel to VPS PostgreSQL, **not** the local DB. Never trust an occupied port without verifying process ownership.
- **Safe checks:** `npm run lint` (frontend TypeScript), `npm run typecheck --prefix backend`; for backend changes, `npm test --prefix backend` **only after** confirming `backend/tests/run.ts` and the DB target are safe: this runner creates/drops a disposable database. Never run DB-writing test files directly against an active database.
- **WinForms checks:** use **Windows PowerShell 5.1** (not PS7 syntax); preserve UTF-8 BOM in scripts that require it. For affected controls, run `powershell.exe -NoProfile -File scripts/test-mita-backend-control-static.ps1`, `scripts/test-mita-desktop-ports-static.ps1`, `scripts/test-mita-sync-control-static.ps1` and/or `scripts/test-mita-tunnel-diagnostic-static.ps1` with the same command prefix. Static tests do **not** prove real layout, login or lifecycle; arrange safe actual WinForms smoke when needed.

## Always
- **Verify live schema compatibility before DB-dependent code ships:** identify the sanitized host/port/database (`current_database()`, `inet_server_addr()`, `inet_server_port()`), then compare required tables, columns and indexes with **read-only live queries** (`information_schema`, `to_regclass`, `pg_indexes`) and SQL files. Migration files and `/api/health` (`SELECT 1`) are not proof the feature schema exists.
- **Ship schema changes coherently:** review queries, additive/idempotent SQL, wiring in `backend/src/db/migrate.ts` **and** `backend/tests/run.ts`, and regression tests together; test upgrading an older schema and reapplying SQL in a disposable DB.
- **Check affected behavior, not only unit tests:** verify successful/error paths and distinguish static checks, disposable-DB tests, real WinForms operation, running worker revision, VPS sync and deployed API. Do not claim one proves another. Report commands/results, environment, revision and remaining gaps.
- **Preserve data semantics:** retain provenance, observed timestamps, source-backed variants/images and last good snapshots. Distinguish title-only translation from full translation, a viewed CAPTCHA page from verified access, and a queued/partial job from completed sync.
- **Use current worker controls:** Owner settings in `worker_control_settings` select the names engine (`openrouter`/`codex`) and JST schedules (defaults 04:00/05:00/05:15); missed jobs do not catch up. The current Supervisor launcher uses `AMAZON_GALLERY_PILOT_DATE=verified`, but a running Supervisor may retain an older environment. Verify process revision, locks and daily status before claiming a scheduled job ran or changing its lifecycle.
- **Treat One-Click as a pinned release, not auto-commit:** `deploy-one-click.bat` operates on the already committed click-time HEAD, with source/SSH/DB checks, catalog sync and verification. It never stages or commits unrelated work; a `main` push with HEAD `[deploy]` triggers release, while One-Click can use guarded `workflow_dispatch` for its pinned SHA. GitHub Actions does not migrate the production database.
- **Keep changes narrow:** no unrelated refactor, dependency changes or generated artifacts without need; review the diff and stage only task paths (`git add -- <paths>`, never blanket `git add .`). Respect pre-existing untracked/modified files and private `.agents/runtime/`.

## Ask first / require explicit authorization
- **Active local/VPS DB changes:** identify the exact target and effects, review SQL/locks and rollback limits, and obtain approval before standalone schema/data changes. The owner's deliberate launch of `deploy-one-click.bat` authorizes only the **currently reviewed, committed normal One-Click path**: (1) local `npm run db:migrate --prefix backend` (the full `backend/src/db/migrate.ts` SQL bundle, not Admin-only); (2) VPS `catalog_deploy_ledger` preflight and transactional `CREATE TABLE IF NOT EXISTS` if missing; (3) VPS `migrate-vps-title-revisions.mjs --apply` with `ADD COLUMN IF NOT EXISTS` for `product_translations.name_revision`, `name_generation`, `name_model`; (4) the separately reviewed VPS checkout migration `migrate-vps-amazon-quotes.mjs` pinned to the exact SHA-256 of `amazon-quotes.sql` (including the `order_items` primary key upgrade, quote tables and checkout columns); and (5) guarded catalog sync/verify and pinned Git release. These unchanged reviewed steps need no separate manual migration command after the owner launches normal One-Click. New/modified SQL, unrelated DB writes, standalone migrations, `-DataOnly` and `-MigrationsOnly` require separate scope review and authorization. **Owner decision reaffirmed 2026-11-06: no VPS backup/dump as part of One-Click.** Do not create one or require a restorable backup as a prerequisite. Rollback is possible only before commit; without an external backup, later data loss cannot be restored. Keep database identity, tunnel ownership, migration scope, locks and sync-claim safeguards.
- **Stateful operations:** obtain authorization and verify ownership, running jobs and locks before starting/stopping/restarting PostgreSQL, Supervisor, workers, gateway, tunnels or VPS services. Edits to worker files may trigger Supervisor auto-reload even without a manual restart; assess that effect first.
- **Network or deploy actions:** `scripts/deploy-one-click.ps1 -DryRun` avoids DB writes/push but still fetches Git, reads DPAPI credentials, opens an owned SSH tunnel and writes runtime logs; it is not an offline check. `git push`, VPS sync, migrations and release actions are separate from ordinary code verification. Editing this policy file does not authorize production operations.

## Never
- **Never migrate/reset implicitly:** do not run `npm run db:migrate`, `scripts/start-local.ps1`, init/reset/truncate DB or change Owner credentials merely to start/fix API. `start-local.ps1` can initialize/start PostgreSQL and runs the full local migration bundle. Normal One-Click's **fixed reviewed** schema steps are the local bundle, conditional VPS deploy ledger, the three VPS title-revision columns, and the checksum-pinned checkout schema above; never silently add further DDL to its authorization. `-MigrationsOnly` also applies VPS translation and nightly-ledger migrations and needs separate approval. Catalog sync itself must not create arbitrary schema or reset a ledger.
- **Never mislabel auth failures:** Owner/Staff login needs `admin_accounts.username`, `role`, `enabled` and `admin_staff_login_limit`. Missing columns produce server errors, **not** bad passwords. Do not mask SQL errors as 401 or repeatedly attempt real Owner login; use synthetic credentials for auth/limiter tests, never real passwords.
- **Never bypass job/source guards:** do not delete sync ledger/leases, force same-JST-day replay, retry an uncertain commit, skip three-worker completion barriers, bypass CAPTCHA/403/429/cooldown gates, or manufacture source facts. A forced rerun needs reviewed idempotency and explicit approval.
- **Never disturb foreign processes or production data:** no generic kill-by-port, unsanctioned DB writes, VPS sync, schema changes or side effects on other services. Keep secrets, tokens, password hashes, cookies and customer data out of logs, reports and Git.
- **Never deploy by accident:** `[deploy]` in the HEAD commit message when pushed to `main` triggers GitHub Actions VPS deployment. Do not push or add this marker without explicit approval; do not run a Next production build against an active dev server's shared `.next` output.
